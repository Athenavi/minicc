# MiniCC Agent 记忆系统四层架构实施方案

> 版本：v1（2026-08-21）
> 状态：设计完成，待评审后实施
> 范围：python-engine 记忆子系统重构 + AgentRuntime 集成 + 前端冲突确认流
> 关联模块：`app/session_store.py`、`app/memory/{manager,store}.py`、`app/context/manager.py`、`app/agent/runtime.py`、`app/agent/prompt_engine.py`、`app/tools/memory.py`

---

## 1. 背景与现状盘点

当前记忆能力散落在四个互不知晓的组件中，各有缺陷：

| 组件 | 现状 | 问题 |
|------|------|------|
| `SessionStore`（main.py:22） | Redis/内存 LRU（max 200），存完整消息列表 | 刷新即失忆；无持久化；无跨会话恢复 |
| `MemoryManager`（memory/manager.py） | 短期 Redis list + 长期 Milvus 向量 | 已被 prompt_engine 注入（:191），但写入无人调用——**只读不写的孤岛** |
| `MemoryStore`（memory/store.py） | 进程内 KV facts + 文件落盘，remember/recall/forget 工具 | 单例全局存储，**无租户/用户隔离**；Go deprecated 兼容层 |
| `ContextManager`（context/manager.py） | token 计数 + 80% 阈值 LLM 摘要 + trim_to_fit | 摘要结果直接丢弃，未沉淀为可检索记忆 |

核心结论：**基础设施都在（Redis/PG/Milvus/嵌入网关/NER/摘要器），缺的是统一架构与流转机制**。本方案不重写存储层，而是收编重组。

## 2. 四层架构总览

```
┌─────────────────────────────────────────────────────────────┐
│                     Agent 主循环（每回合）                      │
│  prompt = 系统提示 + L2档案卡 + L3相关摘要 + L4原始窗口 + 本轮输入 │
└──────┬──────────────┬──────────────┬──────────────┬─────────┘
       │L1            │L2            │L3            │L4
  ┌────▼────┐   ┌─────▼─────┐  ┌─────▼──────┐ ┌────▼─────┐
  │会话元数据 │   │用户档案卡   │  │近期对话摘要  │ │ 滑动窗口  │
  │ 进程内存  │   │ PG JSONB  │  │ Milvus+PG  │ │  Redis   │
  │ 用完即丢  │   │ 精确KV查询 │  │ 唯一语义检索 │ │原始消息序列│
  └─────────┘   └───────────┘  └─────┬──────┘ └────┬─────┘
                                     │巩固          │巩固
                                L4滑出消息 ──摘要──► L3
                                L3稳定事实 ──提炼──► L2（冲突→询问用户）
```

| 维度 | L1 会话元数据 | L2 用户档案卡 | L3 近期对话摘要 | L4 滑动窗口 |
|------|--------------|--------------|----------------|------------|
| **存储内容** | session_id、入口渠道、模式、回合数、token 用量 | 身份、偏好、长期事实、关键决策 | 会话级摘要 + 主题/实体 | 当前对话原始消息（含工具调用） |
| **存储介质** | 进程内存 dict | PostgreSQL JSONB | Milvus 向量 + PG 元数据 | Redis list |
| **访问频率** | 每回合读写（最高） | 每回合读（经缓存）；写低频 | 每回合 1 次语义查询；写每 N 回合 | 每回合读写（最高） |
| **容量限制** | ~1KB/会话；会话数上限沿用 200 | 32KB/用户；≤200 条目 | 注入预算 ≤6KB（top_k=5）；条目保留 90 天 | token 预算由 compaction 80% 阈值控制 |
| **生命周期** | 会话结束即丢弃 | 永久（衰退归档） | 衰退式遗忘 | 窗口滑出→巩固后丢弃 |
| **决策作用** | 路由/计费/审计/降级标记 | 系统提示个性化（"你是谁、你要什么"） | 相关历史召回（"上次聊过什么"） | 当前对话连贯性（"刚才说了什么"） |
| **检索方式** | 键直取 | 键值精确匹配（**不做语义检索**） | 向量语义检索（**全系统唯一**） | 顺序回放 |

设计原则：
1. **语义检索只发生在 L3 一层**——控制嵌入成本与召回噪声，L2 靠结构化槽位、L4 靠顺序。
2. **每层只做一件事**——L4 管连贯、L3 管相关、L2 管稳定、L1 管簿记；跨层靠显式巩固 pipeline。
3. **写路径异步、读路径同步**——巩固/嵌入走后台任务，召回在回合内必须确定路径（缓存兜底）。
4. **不破坏前缀稳定**（L4 评估结论，见 §3.4）。

## 3. 各层详细设计

### 3.1 L1：会话元数据（SessionMeta）

**定位**：回合级簿记数据，纯粹为路由、计费、审计、降级标记服务，与对话内容无关。

**数据结构**（新增 `app/memory/layers.py`）：

```python
@dataclass
class SessionMeta:
    session_id: str
    tenant_id: str
    user_id: str
    entry_channel: str        # "web" | "api" | "quick_execute" | "workflow"
    mode: str                 # agent 模式
    started_at: float
    last_active_at: float
    turn_count: int = 0
    total_tokens_in: int = 0
    total_tokens_out: int = 0
    degraded: bool = False    # LLM 摘要不可用等降级标记
    flags: dict[str, Any] = field(default_factory=dict)
```

**存储与生命周期**：
- 进程内存 `dict[session_id, SessionMeta]`，加 15 分钟空闲 TTL 清理（复用现有 `_evict_if_needed` 思路）。
- **不持久化、不跨实例共享**——会话中断丢失可接受（这些数据可从 trace/审计日志重建）。
- 会话结束（显式 end 或 TTL）→ 触发一次 L4→L3 巩固后整体丢弃。

**访问频率**：每回合 2 次写（turn_count++、token 累计）、按需读（计费/审计）。

### 3.2 L2：用户结构化档案卡（ProfileCard）

**定位**：跨会话稳定的结构化事实。回答"这个用户是谁、偏好什么、做过哪些关键决策"。**只做键值精确查询，不做语义检索**（用户明确要求）。

**数据结构**——PG 单表（迁移 `20260821000003_user_memory_profile.{up,down}.sql`）：

```sql
CREATE TABLE IF NOT EXISTS user_memory_profile (
    tenant_id   VARCHAR(64)  NOT NULL,
    user_id     VARCHAR(64)  NOT NULL,
    slot        VARCHAR(32)  NOT NULL,   -- identity / preference / decision / fact
    item_key    VARCHAR(128) NOT NULL,   -- 槽位内键，如 "timezone" / "preferred_language"
    item_value  JSONB        NOT NULL,   -- 值，允许对象（如 {"value": "UTC+8", "note": "上海时区"}）
    confidence  SMALLINT     NOT NULL DEFAULT 50,        -- 0-100
    source      VARCHAR(16)  NOT NULL DEFAULT "derived", -- user_confirmed / derived / tool_written
    version     INTEGER      NOT NULL DEFAULT 1,
    confirmed_at TIMESTAMPTZ,            -- 用户最后确认时间（NULL=未确认）
    last_referenced_at TIMESTAMPTZ,      -- 最近被召回引用时间（衰退依据）
    created_at  TIMESTAMPTZ  NOT NULL DEFAULT now(),
    updated_at  TIMESTAMPTZ  NOT NULL DEFAULT now(),
    PRIMARY KEY (tenant_id, user_id, slot, item_key)
);
CREATE INDEX idx_ump_reference ON user_memory_profile (tenant_id, user_id, last_referenced_at);
```

Python 侧 db.py `ensure_tables` 同步补建（迁移双轨约定）。

**槽位（slot）设计**——固定四类，新增槽位需改代码：

| slot | 内容 | 典型 item_key | 写入来源 |
|------|------|--------------|---------|
| `identity` | 身份属性 | name / role / org / timezone | 用户显式陈述、SSO 档案初始化 |
| `preference` | 偏好 | output_language / code_style / detail_level | 对话中提炼 |
| `decision` | 关键决策 | "2026-08 决定用 PG 而非 Mongo" 这类带时间戳的决策记录 | 对话中提炼（须 ≥2 次出现或用户确认） |
| `fact` | 长期事实 | "负责 MiniCC 项目"、"团队 5 人" | 对话中提炼、remember 工具 |

**访问与更新规则**：
- **读**：`SELECT ... WHERE tenant_id=? AND user_id=?`，全量 ≤200 条目、≤32KB，整卡读出后经 Redis 缓存（key `memcard:{tenant}:{user}`，TTL 60s，写穿透失效）。**注入 prompt 时整卡序列化为紧凑键值块**（估算 ≤1.5KB）。
- **写**：槽位级 upsert（`ON CONFLICT ... DO UPDATE SET item_value=..., version=version+1`）。
- **冲突规则**（对应用户"冲突记忆询问用户"要求）：
  - 新旧 `item_value` 不一致且旧值 `source=user_confirmed` → **不自动覆盖**，产出 `MemoryConflict` 事件（见 §5.4）；
  - 旧值为 `derived` → 新值覆盖但 `version+1`、`confirmed_at` 置空；
  - 同一事实 `source` 从 derived 升级 user_confirmed → confidence 置 100。
- **遗忘/衰退**：
  - 用户显式 forget → 硬删；
  - `last_referenced_at` 超 180 天且 confidence < 80 → 归档表 `user_memory_profile_archive`（不删，管理端可查）；
  - 用户否认（"我从来没说过 X"）→ 硬删 + 记 `negative_fact` 抑制条目（防止 L3 再次提炼出同一错误事实，抑制名单存 L2 flags）。

**容量**：每用户 200 条目软限，超出按 `confidence × recency` 淘汰最低分 derived 条目。

### 3.3 L3：近期对话摘要（唯一语义检索层）

**定位**：把多轮/多会话对话压缩为"主题 + 关键实体 + 摘要"，跨会话按语义相关召回。**全系统唯一的向量检索单元**——同时天然压缩 token。

**数据结构**——复用现有 Milvus `memory_store` collection（manager.py 已建），扩展 `memory_type` 取值：

```
memory_type ∈ {"summary", "topic", "long_term(legacy)"}
```

每条记忆的 `metadata_json`：

```json
{
  "session_id": "s-xxx",
  "turn_range": [12, 30],
  "topics": ["数据库选型", "迁移策略"],
  "entities": {"person": [], "tech": ["PostgreSQL", "Milvus"], "url": []},
  "rollup_of": ["mem-id-1", "mem-id-2"],
  "content_hash": "sha256:...",
  "access_count": 3,
  "last_accessed_at": 1755753600,
  "status": "active"
}
```

**PG 侧镜像表**（摘要正文与元数据，向量之外的运维视图 + 归档冷存储）：

```sql
CREATE TABLE IF NOT EXISTS memory_summaries (
    id          VARCHAR(64) PRIMARY KEY,
    tenant_id   VARCHAR(64) NOT NULL,
    user_id     VARCHAR(64) NOT NULL,
    session_id  VARCHAR(64) NOT NULL,
    content     TEXT NOT NULL,
    topics      JSONB NOT NULL DEFAULT '[]',
    entities    JSONB NOT NULL DEFAULT '{}',
    content_hash VARCHAR(80) NOT NULL,
    access_count INTEGER NOT NULL DEFAULT 0,
    last_accessed_at TIMESTAMPTZ,
    status      VARCHAR(16) NOT NULL DEFAULT 'active',  -- active/archived
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_ms_lookup ON memory_summaries (tenant_id, user_id, status, created_at DESC);
CREATE UNIQUE INDEX uq_ms_hash ON memory_summaries (tenant_id, user_id, content_hash);
```

**生成 pipeline**（复用现有组件）：
1. **摘要文本**：复用 `ContextManager._summarise`（LLM 摘要，gateway 调用）；
2. **实体抽取**：复用 TaskRouter 的规则式 NER（task_router.py:760，8 种实体零依赖）；
3. **主题提炼**：LLM 摘要 prompt 中要求输出 `topics: [...]` 行，正则解析；
4. **嵌入**：复用 `gateway.embed`（llm client 本地优先 + 网关回退链路）。

**检索与排序**：

```
final_score = cosine_similarity          # Milvus COSINE，nprobe=10（沿用现有参数）
              × recency_decay            # exp(-Δdays / 30)
              × (1 + 0.1 × min(access_count, 10))
```

- 查询入口 `recall(query, top_k=5)`；**注入预算硬上限 6KB**（超出按 final_score 截断）。
- 命中即 `access_count += 1`、`last_accessed_at = now()`（写合并：Redis 计数缓冲，5 分钟批量刷 PG，见 §7）。
- 阈值：cosine ≥ 0.45（略低于现有 0.5，配合 recency 加权后由排序裁决）。

**遗忘/衰退规则**：
- `status=active` 且 90 天未命中 → 后台任务置 `archived`（Milvus 侧 `metadata_json.status` 同步）；
- archived 条目不参与召回，保留 1 年后删除；
- 同 `topics` 下条目 > 20 条 → 触发 rollup（多条旧摘要合并为一条新摘要，旧的转 archived）——即"记忆压缩"。

### 3.4 L4：滑动窗口（当前对话原始上下文）

**定位**：管理当前会话的原始消息序列（含工具调用消息），保住对话连贯性。

**用户要求的评估结论（滑窗 vs 现有方案）**——现有方案必须保留为主：

| 方案 | 机制 | 对网关 LLM 会话缓存的影响 |
|------|------|--------------------------|
| 现有（保留）：SessionStore append-only + ContextManager compaction | 消息只追加；token 超预算 80% 时，LLM 摘要中段、保留头尾（retainTokens），前缀保持稳定 | **前缀稳定 → 缓存命中率高**（runtime.py:704 注释明示此设计意图） |
| 朴素滑窗（否决）：超限直接丢最旧消息 | 窗口滑动 | 前缀变化 → **每回合缓存全失效**，成本与延迟双升 |

**采用的混合方案——"摘要式滑窗"**：
1. 消息序列保持 **append-only**（前缀稳定，缓存命中不受损）；
2. token 预算达到 80% 阈值 → 走既有 compaction：**滑出部分先巩固到 L3（摘要入库），再以摘要块替换**——窗口"减小"通过摘要替换实现，而非删除；
3. compaction 依赖的 LLM 摘要服务不可用 → **降级链**：先重试 1 次 → 仍失败则 `trim_to_fit`（硬截断，标记 `L1.degraded=True`）→ 回合结束把待摘内容补交后台巩固队列。**这是全记忆系统唯一允许 fail-soft 的点**（宁可丢中段历史也不让对话失败），其余路径维持 fail-loud。
4. 窗口滑出的原始消息在巩固确认（L3 写入返回 memory_id）**之前不得从 SessionStore 删除**——保证崩溃恢复时不丢数据。

**容量**：token 预算 = 模型上下文 × mode 配置（沿用 CompactionConfig thresholdRatio/retainTokens），回合硬上限由 `trim_to_fit` 兜底。

## 4. 层间流转与同步机制

### 4.1 巩固（Consolidation）：L4 → L3 → L2

**触发时机**（三个入口，全部异步入队，复用 `app/queue` 模块）：

| 触发 | 时机 | 动作 |
|------|------|------|
| 滚动巩固 | compaction 执行时（滑出内容） | 滑出消息 → 摘要 → L3 |
| 会话收尾 | `on_session_end`（显式结束 / TTL） | 整会话 rollup 摘要 → L3 |
| 定期 rollup | 每日凌晨 | 同主题 >20 条 → 合并压缩 |

**巩固 pipeline 步骤**（`app/memory/consolidator.py`）：

```
滑出消息 → ① LLM 摘要（ContextManager._summarise）
        → ② NER 实体 + 主题解析
        → ③ 去重检查（content_hash 精确 + 嵌入 cosine>0.95 近重复 → 合并）
        → ④ 写 L3（Milvus insert + PG 镜像，双写）
        → ⑤ 稳定事实探测：entities/topics 命中 L2 既有槽位 or 出现 ≥2 次跨会话
             → 是 → 产出"档案卡候选"（pending_confirmation 表）
             → 否 → 结束
```

**L3 → L2 的准入门槛**（防止把闲聊固化成档案）：
- 用户显式陈述句式（"记住我用的是上海时区"）→ 直接写入，`source=user_confirmed`；
- Agent 提炼 → 先入 `pending_confirmation`（Redis，TTL 7 天）：
  - 同一候选**第二次**出现 → 自动写入，`source=derived, confidence=60`；
  - 与既有条目冲突 → `MemoryConflict` 事件 → 询问用户（§5.4）；
  - 7 天未复现 → 丢弃。

### 4.2 检索与召回（每回合 prompt 组装）

```
recalled = await memory.recall(
    scope=Scope(tenant_id, user_id, session_id),
    query=当前用户消息 + 最近1条助手消息拼接,
    token_budget=8_000,   # L2(1.5KB) + L3(6KB) 的总预算
)
```

组装顺序（注入 prompt_engine 的记忆上下文区，:187 挂点扩展为分段）：

```
[系统提示]
── 记忆：用户档案 ──        ← L2 整卡紧凑序列化（≤1.5KB，含 confidence≥50 的条目）
── 记忆：相关历史 ──        ← L3 top_k=5 按 final_score 排序（≤6KB）
[L4 原始窗口消息（前缀稳定）]
[本轮用户输入]
```

**关键规则**：
- L3 召回结果与 L4 窗口内容做**简单包含去重**（摘要覆盖的 turn_range 与窗口重叠 → 丢弃该摘要，窗口原始内容优先）；
- L1 不进入 prompt（纯簿记）；
- 召回失败（Redis/Milvus 异常）→ 该段缺省 + 日志告警，**不阻断回合**（读路径 fail-soft，与写路径 fail-loud 区分）。

### 4.3 更新与遗忘规则汇总

| 层 | 更新 | 遗忘 |
|----|------|------|
| L1 | 每回合原地改写 | 会话结束整体丢弃 |
| L2 | 槽位 upsert + version 递增；冲突须用户裁决 | 显式 forget / 用户否认 → 硬删；180 天未引用且低置信 → 归档 |
| L3 | access_count 累积；rollup 重建 | 90 天未命中 → archived；归档 1 年 → 删除 |
| L4 | append-only；compaction 摘要替换 | 滑出内容巩固确认后才可清理 |

## 5. 接口规范

### 5.1 核心门面：MemoryService

新增 `app/memory/service.py`，组合四层 provider，**对 AgentRuntime 是唯一入口**：

```python
class MemoryService:
    def __init__(self, session_meta_store, profile_card, summaries,
                 session_cache, gateway, queue=None): ...

    # ── 会话生命周期 ──
    async def on_session_start(self, meta: SessionMeta) -> SessionContext:
        """L1 建立；从 PG/Milvus 恢复该用户 L2 档案卡缓存 + 最近 3 条 L3 摘要预取。"""

    async def on_turn_complete(self, session_id: str, messages: list[dict],
                               usage: TokenUsage) -> None:
        """L1 记账；L4 append（内部判断 compaction 触发）；异步入队巩固。"""

    async def on_session_end(self, session_id: str) -> None:
        """触发会话级 rollup 巩固 → L1 丢弃。"""

    # ── 读路径（每回合，同步、fail-soft）──
    async def recall(self, scope: Scope, query: str,
                     token_budget: int = 8_000) -> RecallResult:
        """返回 RecallResult(profile_block: str, summary_items: list[RecalledItem])。"""

    # ── 写路径 ──
    async def save_summary(self, scope: Scope, content: str,
                           turn_range: tuple[int, int]) -> str:
        """L3 写入（巩固 pipeline 内部调用；也暴露给测试）。返回 memory_id。"""

    async def update_profile(self, scope: Scope, slot: str, key: str,
                             value: Any, *, confirm: bool = False) -> ProfileUpdateResult:
        """L2 upsert。confirm=True 表示用户显式确认；冲突时返回 pending 的 ConflictRef。"""

    # ── 删除 ──
    async def forget(self, target: MemoryRef) -> bool:
        """MemoryRef = ("profile", slot, key) | ("summary", memory_id)。"""

    # ── 冲突 ──
    async def list_conflicts(self, user_id: str) -> list[MemoryConflict]: ...
    async def resolve_conflict(self, conflict_id: str, resolution: str,
                               manual_value: Any = None) -> None:
        """resolution ∈ {"keep_old", "adopt_new", "manual"}。"""
```

### 5.2 与 Agent 主循环集成

改造点集中在 `runtime.py`（现 425-426 加载、704-706 保存两处）：

  await memory.on_turn_complete(session_id, messages, usage) # ← L4 append + compaction 编排

## 7. 性能与可扩展性

**缓存策略**：
- L2 档案卡：Redis 60s TTL + 写穿透失效；命中路径零 PG 查询；
- L3 查询结果：`sha256(query + user_id)` 为 key 的 5 分钟 Redis 缓存（同 query 重放零嵌入零检索）；
- 嵌入查询向量：同 key 缓存 30 分钟。

**批量写入**：
- 巩固任务经 `app/queue` 异步执行，**绝不阻塞回合**（on_turn_complete 只入队）；
- Milvus insert 攒批（32 条或 500ms flush 节流，复用 flush 语义）；
- L3 access_count/last_accessed_at 更新走 Redis 计数缓冲，5 分钟批量 UPSERT PG。

**记忆压缩与去重**：
- 精确去重：content_hash 唯一索引（PG 层拦截）；
- 近重复：巩固时新摘要与同 topics 既有摘要嵌入比对，cosine > 0.95 → 合并（保留新，旧的 archived，`rollup_of` 记录 lineage）；
- rollup 压缩：同主题 >20 条 → LLM 合并为单条（token 成本 O(log n) 增长而非线性）。

**持久化与跨会话恢复**：
- L2 = PG（天然持久）；L3 = Milvus + PG 双写；L4 会话结束 dump 到 PG `conversations`（衔接"会话持久化"规划项，新会话可整体恢复）；
- 崩溃恢复：L4 append 顺序写 Redis（现有 SessionStore 已保证）；巩固采用"先写 L3、后清 L4"的确认顺序，最坏情况重复巩固一次（幂等去重兜底）；
- 跨实例：L1 进程内存（可丢）、其余层共享存储，多 worker 部署天然兼容。

**容量护栏**（配置项，settings 扩展）：

```python
memory_profile_max_items: int = 200
memory_summary_top_k: int = 5
memory_recall_token_budget: int = 8_000
memory_summary_retention_days: int = 90
memory_profile_archive_days: int = 180
memory_consolidate_batch: int = 32
```

## 9. 风险与开放问题

1. **LLM 摘要质量**：巩固摘要失真会把错误固化进 L3/L2。缓解：摘要 prompt 要求保留实体原文；用户可经 Profile 页查看/删除全部记忆（透明可控）。
2. **嵌入成本**：每次巩固 1 次 embed + 每回合 1 次查询 embed。缓解：查询缓存 + 攒批；本地 sentence-transformers 优先链路已就绪（llm/client）。
3. **Milvus 不可用**：读路径 fail-soft（该段缺省）；写路径入队重试，队列积压超限告警。
4. **隐私合规**：记忆默认租户内隔离；提供"清空我的记忆"（级联 L2/L3/归档）作为 PR-4 API 补充项。
5. **L4 评估遗留**：若实测发现 compaction 头尾保留策略与超长工具调用序列冲突（retainTokens 内放不下），需引入"工具结果引用化"（工具大输出转存对象存储、窗口留指针）——列为观察项，不在本期实施。
